## grok の大型 pack 欠席（argv 上限）を解消

取り込んだ改善メモの中で最頻の再発だった、`run_grok.sh` の argv 渡し問題に対処した。

### 症状と原因

`run_grok.sh` は CLI 経路で `grok -p "$PROMPT"` と **argv** でプロンプトを渡していた。
Linux の単一引数長の上限（`MAX_ARG_STRLEN` ≒ 128KB。`ARG_MAX` 2MB とは別物）を超えると
exec 自体が `Argument list too long` で失敗し、**grok だけが無言で空応答**になる。
実装レビュー型の大型 pack（148〜238KB）で4回再発していた
（IMPROVEMENTS 2026-07-25 ×2 / 07-30 / 08-05）。codex/gemini/claude は元から stdin 渡しで無傷。

再現も取った。248KB のプロンプトで `grok -p "$(cat big.md)"` → `argument list too long: timeout`。

### 採った手段: `--prompt-file`

Grok Build CLI の `--help` を確認したところ **`--prompt-file <PATH>`（Single-turn prompt
from a file）** があった。IMPROVEMENTS の案は「空 WORK_DIR に prompt.md を置いて
『このファイルを読んで回答せよ』と指示する」だったが、それはエージェントの読み取り挙動に
依存する。`--prompt-file` は CLI 自身がファイルを読んで単発プロンプトにするので、より直接的。

実機で確認:
- 248KB の `--prompt-file` → 期待どおりの回答（`BIGPONG`）を stdout に返す
- `run_grok.sh` 経由の E2E（ガード前置込み・248KB）も成功

プロンプトファイルは **WORK_DIR の外**（別 `mktemp -d`）に置いた。空 CWD で隔離している
意図を壊さないため（CWD に置くと「読めるファイルがある」状態になる）。
副次的に、argv 経由で実行中 `ps` にプロンプト全文が見える問題も消えた。

### 併せて入れたもの

1. **旧 CLI 向けフォールバックの明示エラー化**: `--prompt-file` 非対応の CLI では従来どおり
   `-p` に落ちるが、`QUORUM_MAX_ARGV_BYTES`（既定 120000）を超えたら
   `invalid_response:argv-too-long` を stderr に出して **exit 4**。無言の空応答にしない。
2. **`check_answer.sh` に第2引数 stderr**: 空応答のとき stderr に
   `Argument list too long` / `argv-too-long` があれば `invalid_response:argv-too-long` と
   名指しする。従来は `empty` としか出ず、原因特定に `.err` を人が読む必要があった。
3. **SKILL の回収手順で stderr を保存**: `run_<name>.sh 2>"$RUN_DIR/answer_<label>.err"`。
   空応答の原因は stderr にしか出ないため。Claude版・Codex版の両方に反映。
4. **run_*.sh 規約に明記**: 「プロンプトを argv に展開しない（stdin かファイル渡し）」を
   SKILL のバックエンド規約と README「パネリストを足す」の 4 項目目に追加。

### 検証

- `bash tests/run_tests.sh` … **121 件 ALL PASS**（105 → 121。grok 8件・check_answer 5件・
  連携1件・モデル指定1件・フォールバック2件を追加）
- 新テストは `--prompt-file` 対応/非対応の 2 種の mock CLI を用意し、本線とフォールバックの
  両経路、270KB のプロンプト全量到達、exit 4、`check_answer` との連携までを見る
- `bash -n` 全スクリプト OK
- 実機 E2E: 248KB pack を `run_grok.sh` に stdin で流して回答取得（上記）

## 残 TODO の処理（gemini 関連を除く3件）

### 1. codex の collab 無効化フラグ（調査 → 恒久化）

`codex exec` は重いタスクほど「監査を3領域に分割」と宣言して collab spawn を試み、
`collab spawn failed: no thread with id` を繰り返した末にタイムアウトする
（IMPROVEMENTS 2026-07-13）。exec + `--ephemeral` + 空 WORK_DIR では collab が動かないのに、
モデルからは使えるように見えているのが原因。ガード前置は実装済みだったが、フラグの有無は未調査だった。

**見つかった**: codex-cli 0.144.1 には機能フラグ機構があり（`codex features list`）、
collab/サブエージェントに当たるのは **`multi_agent`（stable / 既定 true）**。
`codex exec --disable multi_agent` で個別に落とせる。

実機で確認した:
- `codex features list --disable multi_agent` → `multi_agent ... false` に変わる
- run_codex.sh と同じフラグ一式に `--disable multi_agent` を足して実行 → 正常に回答（`PONG`）

`run_codex.sh` に `codex exec --help` の capability probe つきで恒久化した（旧 CLI には渡さない）。
**プロンプト側のガードは残した**——フラグ名も存在も CLI バージョン次第で変わるため、二重の歯止めにする。

正直に書いておくと、「collab ツールがモデルに提示されていない」ことの**直接証明は取れていない**。
`--json` の JSONL にツール定義が出ないため、根拠は features フラグの状態変化までである。

### 2. 連続欠席の警告

opt-in 済みの backend が認証切れ・CLI 更新で恒久的に落ちていても、毎回「一時的な欠席」として
無言でネイティブ補完され、パネルが静かに同族寄りへ退化する（IMPROVEMENTS 2026-07-10）。

**前提として `--check` の exit code 規約を拡張した**。これが無いと、opt-out しているPCで毎回
警告が出て無意味になる:

| code | 意味 |
|---|---|
| 0 | 可用 |
| 2 | **意図的に不参加**（opt-out・未設定・`ANTHROPIC_API_KEY` の課金ガード） |
| その他非0 | 参加したいのに使えない（CLI 未導入・認証切れ・キー無し） |

全 run_*.sh に反映。`run_claude.sh` は判定順も入れ替えた（課金ガードを CLI 存在確認より前に）
——ガードが効いている状態を「CLI が壊れている」と誤って連続欠席に数えないため。

`detect_panel.sh` 側は、2 以外の失敗だけをカウントし、既定3回連続で **stderr** に警告を出す
（`QUORUM_ABSENCE_WARN`、`0` で無効）。stdout はパネル multiset で SKILL が1行=1パネリストとして
読むので、警告は必ず stderr。状態は `$QUORUM_STATE_DIR/absence.tsv`（既定 `~/.local/share/quorum`）。

**置き場を runs/ にしなかった**理由: runs/ は1実行の生入出力で、横断カウンタを置くと読み手が
増えるだけだった。専用の小さな状態ファイルにした。

### 3. 実質回答なし検知のハードゲート格上げ → **見送り（データ不足）**

格上げの前提は「誤棄却が出ていないことを実データで確認」。しかし
`~/.local/share/quorum/runs` を調べたところ、**checks.txt を持つ run は0件**だった
（7 run はすべて check_answer.sh 導入前。蓄積は利用側PCにある）。裏付けが無いまま
自動棄却へ進めない、と判断して見送った。

代わりに、判断を毎回手作業にしないための `scripts/checks_summary.sh` を追加した。
過去 run の checks.txt を横断集計し、**バイト数の大きい順＝閾値に近い＝誤棄却の疑いが濃い順**に
並べて冒頭120バイトを見せる。上位に実質的な回答が1件でもあれば見送り、
「これから確認します」型の途中報告ばかりなら格上げしてよい、という判定手順まで出力に書いた。

PROGRESS の当該 TODO は「データ待ち」と明記し、実行すべきコマンドを添えた。
なお同 TODO にぶら下がっていた「巨大 pack 時の grok 自動降格閾値・ファイル渡し方式」は、
`--prompt-file` 化で解消したので取り下げた。
