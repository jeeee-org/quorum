### 発端

ユーザーから `IMPROVEMENTS.md` の内容がコピペで共有された。正本（35件）と突き合わせたところ、**新規は末尾の1件だけ**だった：

共有分の既存35件は正本の「反映」行を含む最新世代と一致していたので、並びのずれ・取りこぼしの追い込みは不要だった（2026-08-09 に規約を古い順・末尾追記へ揃えた効果。`test_improvements_order.sh` も通る）。

### メモの中身

設計レビューを2巡回した実走。**2巡目の pack に「1巡目の指摘を箇条書きで入れ、閉じたかを問う」形が効いた**（3体とも指摘 ID を引いて答え、judge の突き合わせが1巡目より圧倒的に速い）。一方でこの型は SKILL に書かれておらず毎回その場で組んでいる。**1巡目の `judge.md` を渡すかどうか**も迷いどころで、実走では opus 枠にだけ渡した＝可視性が非対称になった。

### 実装（`references/context-packing.md` に1節・両SKILLから参照）

新設: **「2巡目（再レビュー）は『前巡の指摘が閉じたか』を問う形に組む」**

1. **前巡の指摘を ID つきで列挙する**。改善案の「ID つきで列挙」に**「要約でなく指摘の本文を貼る」**を足した——ID だけでは pack しか読めない体に中身が届かない。「何を直したか」は本文でなく「材料の版（正本）」欄の SHA 差分で示す。
2. **回答を3分割で要求する**（①指摘ごとの判定 ②新しい欠陥 ③総合判定）。②の理由を明記した：**明示しないと全員が①だけを埋め、修正自身が持ち込んだ欠陥が誰にも見られないまま通過する**。
3. **前巡の judge 成果物を渡す枠と渡さない枠を混ぜない**。

加えて pack テンプレへ「## 前巡の指摘（再レビュー時のみ・ID つき本文）」欄を追加し、両 SKILL の step 2（Codex版は手順1）から新節を参照させた。

### 判断が要った2点

**1. ③は新しい規則ではなく、既存規律の適用として書いた**

step 2 には既に「**全パネリストに完全に同じプロンプトをそのまま渡す**」がある。実走の非対称はこの規律の違反であって、規律の不足ではない。∴ 新ルールを増やさず、「2巡目は『1巡目の `judge.md` はリポを読める枠だけが読める』形に**黙って**なりやすい」という**破れ方の注意**として書いた。ルールを増やすと守る対象が増えるだけで、気づけない構造は変わらない。

**2. 前巡の judge を渡すか＝既定は「渡さない」**

メモは迷いどころとして提示しただけなので、方針をこちらで決めた。**指摘リストだけを渡し、judge の判定・重みづけは渡さない**を既定にした：

- judge の結論を配ると全員がそこにアンカーされ、独立実行から収穫するという前提（`panel.md`「ブラインドを守る」）が縮む。
- 閉じたかの判定に要るのは**指摘の本文**であって、judge がどう重みづけたかではない。
- どうしても非対称にするなら、mapping.txt ＋監査証跡に「どの枠が前巡の judge を見たか」を可視性（3列目）と同じ粒度で書く（改善案③のとおり）。**非対称そのものより、非対称が記録されずに合意が読まれることが害**。

### 既存機構との接続（メモに無かった追加）

3分割を要求したら、**その見出し語を `check_answer.sh --expect` に渡す**を追記した。2巡目は「1巡目で全部見たから」と作業予告だけ返す体が出やすく、バイト数の検査だけでは通り抜ける（588B の予告がすり抜けた実績。IMPROVEMENTS 2026-08-15）。既に持っている検査に繋ぐだけで、新しいコードは要らない。

## 利用側の改善メモ2件（diff の範囲ミス／Consensus の1段掘り）を取り込み、実装まで完了

### 発端

同日2度目のコピペ共有。正本（36件）と突き合わせた差分は3点：

- 新規 `2026-08-19 — pack に入れる diff の範囲を間違えると、レビュー結果が丸ごと狂う`
- 新規 `2026-08-19 — 「全員が同じ欠陥を挙げた」の中に食い違いが埋まる型`
- 既存 `2026-08-15 — Codex 版の配置を任意化してほしい` への追記（`--no-codex` を使う側が導入し、パネリストとしての codex が無傷であることを確認した報告）

3点目は**こちらの実装に対する使う側からの検証報告**なので、実装は不要でそのまま正本へ取り込んだ。「既存の配置は自動削除しない」判断が使う側から見ても正しかった、という裏取りが得られた。

### メモ1: diff の範囲ミス（材料の誤りは多数決で検出できない）

`git log -p <マージコミット>~2..<HEAD>` の `~2` が前のサブタスクの commit を指し、1つ前の変更3件が「今回の変更」として pack に混ざった。codex が**最重要の欠陥として「既存コードを変更しており設計違反」**を挙げたが、その変更は今回1行も触っていない。judge が範囲を検算して却下した。

実装 = `references/context-packing.md` に **「コードの差分を貼るときは範囲を検算してから貼る」節**を新設：

1. 範囲は `<分岐した commit>..<HEAD>` を**明示指定**（`~N` はマージコミットで親が2つあるため直感と食い違う）
2. 貼る前に `git log --oneline <範囲>` で**レビュー対象と一致することを目視**
3. pack テンプレへ **「## この変更で触ったファイル（コード差分を貼る時のみ）」欄**を追加
4. judge 側の受け = `judge_rubric.md`「judge 自身が確かめる」表に **「スコープ外の変更がある／材料の版が違う」型の行**

加えて「絞り込みの原則」へポインタ1行、両 SKILL の step 2（Codex版は手順1）へ範囲の取り方を書いた。

**判断**: 同日メモが併記していた「`insert_row` の本体を pack に載せず、pack-only の2体が揃って誤った」件を**同じ節の脚注として併記**した。別項目に分けず束ねたのは、どちらも原因が「pack に何を入れたか」で**パネルの質ではない**という点で同型だから（→ 既存の「pack は司書の盲点を継承する」の系）。

### メモ2: Consensus の1段掘り

3体全員が**同じ1行**を最重要欠陥に挙げたが、**倒れる向きが2体で正反対**だった（偽陰性 vs 偽陽性）。再現したら両方成立。rubric の Consensus は「同じ結論に達したか」で束ねるので、**同じ場所・違う機序**が Contradictions へ回らず裁定が飛ばされる。

実装 = `judge_rubric.md` の分析軸 Consensus に「**『同じ結論』は『同じ理由』を意味しない**——根拠・機序・影響の向きまで1段掘り、食い違ったら Contradictions へ移す」を入れ、表の下に実例を添えた。**両 SKILL の judge 手順の Consensus 行にも同じ1行を置いた**——rubric を読み込まずに走る回でも効かせるため（rubric 側だけに書くと、SKILL の箇条書きだけを見て走る経路で落ちる）。

### メモ2の「もう1点」: アクセス権の多様性を表にした

改善案は「panel.md の『アクセス権の多様性』に具体例として追記」だったが、panel.md には**その名前の節が無く**、概念は context-packing.md と judge_rubric.md に分散していた。∴ `panel.md` に **「アクセス権の多様性は、見つかる欠陥の種類を分ける（枠を削る判断の材料）」節**を新設し、08-03 / 08-18 / 08-19 の3実走を**表**で積んだ。

散文でなく表にしたのは、改善案の狙いが「**枠を削る判断のときに効く**」＝どちらの列を失うかを見比べることだから。以後の実走で行を足していけば、判断材料が自動的に濃くなる。締めに「費用や待ち時間で枠を削るときは、この表のどの列を失うかを先に言う」を置き、既存の「連続欠席を理由に外さない」（08-18）へも接続した。
