# context-packing — quorum に渡す前の「司書」手順

quorum 自体は材料を自動収集しない。外部CLIパネリストに届くのは `$PROMPT` のテキストだけで、
呼び出し元のリポやライブ状態は見えない。ネイティブ・サブエージェントにも同じ材料だけを渡して
比較条件を揃える。∴ **「何を入れて何を捨てるか」はメインセッション（＝司書）の責任**。
巨大MD・複数ファイル・MCP のライブ状態に判断材料が散らばっている時、
fan-out（SKILL.md step 2）の前に `$PROMPT` を**自己完結**に組み上げる手順を定型化する。

## いつ使うか
- **使う**: 高ステークスで、判断材料が巨大MD／複数ファイル／ライブ状態に散在（SRE 型）。
- **使わない**: 低ステークス、または材料が小さく問い単体で完結する時は、素の問いをそのまま渡す。

## 司書の5手順
1. **決定文を1〜2文に固める** — 「何を判断したいか」「成功条件・制約は何か」。ここがブレると全員が別の問いに答える。
2. **広く集める** — `grep`/`glob`/`read` ＋ インフラ閲覧スキル ＋ MCP で関連箇所を**広めに**取得。
3. **絞る（最重要）** — トークン予算を決め、**決定を動かす断片だけ**残す。各断片に出典（`file:line` or コマンド名）を付ける。
4. **context pack を組む** — 下のテンプレで自己完結化。パネリストは前提も背景も知らない前提で書く。
5. **渡す** — `$PROMPT = 決定文 + context pack`。`/quorum` に流す（fan-out 以降は SKILL.md 通り）。

## 絞り込みの原則
- **関連性 > 網羅性**。決定を動かさない情報は載せない（コスト N 倍＋長文脈劣化＝context rot）。
- **出典必須**。各事実に `file:line` かコマンド名。パネリストが「裏取り済みの事実」と「司書の仮説」を区別できる。
- **鮮度を明示**。ライブ状態（MCP 由来など）は**取得時刻**を添える（例 `@2026-06-16T10:00`）。
- **前提命題の根拠は原文で貼る**（設計・実装レビュー型）。「現状こう動いている」という命題は、要約・擬似コードで代替せず、**根拠となる関数・分岐を全文引用**する。詳細は下の「pack は司書の盲点を継承する」。
- **コードの差分は範囲を明示し、貼る前に検算する**。`~N` のような相対指定はマージコミットで直感と食い違い、**前のサブタスクの変更が「今回の変更」として混ざる**。詳細は下の「コードの差分を貼るときは範囲を検算してから貼る」。
- **材料は正本 branch から直接取る**。`cat` した手元の clone が pull 前だと、**旧版が外部パネリストへ渡る**。`git show <branch>:<path>` で正本から生成し、**版数・状態行・commit SHA を pack に書く**。judge は回答内の引用をその SHA と機械照合する（2026-08-08 に、worktree push 後の main clone 未 pull で旧版契約が2体に渡り、refute 不能の偽 mustFix を生んだ）。
- **矛盾はそのまま渡す**。司書が解決せず「ここが食い違う」と明示 → judge の Contradictions / Blind spots が働く（解決済みにすると盲点を潰せる利点が消える）。
- **機密は出さない**。外部CLIに渡る前提（学習・キャッシュされ得る）。シークレット・PII・社外秘はマスク or 除外。← SRE 環境では特に必須。
- **落としたものを1行残す**。「大量にあるログのうち直近1hのみ採用」等。無音の切り捨てはしない（SKILL の `panel.dropped` と同じ精神）。
- **整形にバイト単位の切り出しを使わない**。`cut -c` / `head -c` は文字でなくバイトで切る（GNU coreutils の `-c` は実質バイト）ので、日本語 pack では UTF-8 マルチバイト文字の途中で切れて不正バイト列が混入する。外部CLIパネリストの文字化け・解釈不能の原因になる。行単位（`head -n` / `sed -n`）か Python の文字列処理で切る。

## context pack テンプレ（コピペ）
````
## 判断したいこと（決定文）
<1〜2文。成功条件・制約も書く>

## 材料の版（正本）
- <path> @ <branch> <commit SHA 短縮> / 状態: <draft|承認済み|…>
- 生成方法: git show <branch>:<path>

## 前提・背景（パネリストは何も知らない前提で）
<対象システムの一言説明／効いてくる制約>

## 証拠（出典つき・絞り込み済み）
- [src: path/to/runbook.md:120-145] <要点だけ抜粋>
- [src: $ kubectl get deploy -n prod @2026-06-16T10:00] <ライブ状態の要点>
- ...

## 前提命題の根拠コード（設計・実装レビュー型では必須・原文のまま）
```<lang>
// [src: path/to/file.py:88-121]
<「現状こう動いている」を支える関数・分岐の全文>
```

## この変更で触ったファイル（コード差分を貼る時のみ）
- 範囲: `<分岐した commit>..<HEAD>`（`git log --oneline <範囲>` で目視済み）
- <path/to/a.py> / <path/to/b.sh> …（diff に現れるファイルの一覧）

## 既知の食い違い・不明点
- <MD 同士の矛盾／未確認事項／取得できなかったもの>

## 前巡の指摘（再レビュー時のみ・ID つき本文）
- [F1] <1巡目の指摘の本文をそのまま>
- [F2] ...
（回答は「①ID ごとに 閉じた/部分/閉じていない ②新しい欠陥 ③総合判定」の3分割で書くこと）

## 問い
<答えてほしいこと。判断・リスク・盲点を求める形にする>
<生データを添えたなら: 「pack の主要数値を生データから再現し、一致/不一致を報告せよ」を明記>
````

## SRE 環境での当て方（insights #10「司書＋専門家会議」）
- **司書＝メインホスト（Claude Code / Codex）**：利用可能なツールでライブ状態、巨大 MD を retrieval。上の5手順で pack 化。
- **quorum＝専門家会議**：pack を全パネリストに同一プロンプトで配り、judge が Consensus/Contradictions/Blind spots を出す。
- **将来 TAKT へ移す時**：pack 化（手順2-4）は TAKT の step 入力整形に**そのまま移植**できる。retrieval を MCP に寄せておくほど移植が楽（戦略投資は MCP）。

## pack は司書の盲点を継承する（設計・実装レビュー型で効く）

pack を書くのは judge 自身なので、**pack は judge の理解の誤りまで含めて固定する**。
pack の自己完結性は「外部パネリストが読める」ことは保証するが、「前提が正しい」ことは保証しない。

- 実例（2026-07-27）: 既存機構を**擬似コードで要約**して pack に入れたところ、pack しか読めない外部2体は
  judge と同じ前提の枠内でしか指摘できず、**リポを読める opus だけが主症状の取り違えを発見した**
  （「フッターは判定結果によらず 100% 投稿されている」）。
- ∴ **「現状こう動いている」という前提命題は、根拠となる関数・分岐を原文で貼る**。要約・擬似コードで代替しない。
- ∴ **リポを読めるパネリストが混在する構成では、その1体に「pack の前提命題を実装で裏取りせよ」と明示指示する**
  （今回は偶然 opus が自発的に読んだだけ）。これは異種ベンダーとは別軸の多様性＝**アクセス権の多様性**。
- ∴ 生データを添えるなら「見てよい」ではなく「**主要数値を再現して一致/不一致を報告せよ**」と成果物を要求する。
  パネルはパスを渡されただけでは読みに行かないことがある（2026-08-04。3体中1体しか再パースせず、
  再パースした1体だけが判定を左右する事実を2件覆した）。

## 改修レビューでは「その改修が壊しうる既存の検査基盤」を列挙して入れる

diff と試験だけを渡すと、pack-only の体は**差分の中の正しさ**しか見られない。**差分の外側にある前提の破壊**が構造的に死角になる。

2026-08-18 のデータ生成器レビュー（opus / codex / grok）では、pack に背景・要件・git diff・実測値・観点を入れたが、**リポを読める opus だけがデグレを検出した**——「この改修が、常設の連番点検・裁定台帳・既知リストとの厳密一致試験の前提を動かす」という波及で、pack にその連鎖を追う材料が無かった。3体の指摘は「試験の穴」に集中し、**一見よく合意しているように見えたが、合意していたのは pack に入っていた範囲だけ**だった。

∴ 改修対象を**入力にしている**ものを探して列挙する：

1. **その値を読む検査スクリプト**（常設の点検・CI ゲート・lint）
2. **期待値を固定した台帳・golden**（裁定台帳・既知リスト・スナップショット）
3. **厳密一致を要求する試験**（完全一致・件数固定・順序依存）

「合意が取れている」と見えた時ほど、**合意の範囲が pack の範囲と一致していないか**を疑う。

## コードの差分を貼るときは範囲を検算してから貼る

**pack の材料が誤っていると、パネリストの推論が正しくても結論は誤る**——しかも全員が同じ誤った材料を見るので、**多数決でも合議でも検出できない**。judge が範囲を検算して初めて解ける。

2026-08-19 の実装レビューでは、`git log -p <マージコミット>~2..<HEAD>` で差分を貼ったところ、**`~2` が前のサブタスクの commit を指していて**、1つ前の変更3件が「今回の変更」として混ざった。codex は**最重要の欠陥として「既存コードを変更しており設計違反」**を挙げたが、その変更は今回1行も触っていない。検算しなければ実装を巻き戻していた。

1. **範囲は `<レビュー対象が分岐した commit>..<HEAD>` を明示的に取る**。`~N` / `HEAD~N` の相対指定を使わない——**マージコミットは親が2つある**ので `~N` は直感と食い違う。
2. **貼る前に `git log --oneline <範囲>` を実行し、出てきた commit がレビュー対象と一致することを目視する**。この1手で今回は防げた。
3. **pack に「この変更で触ったファイルの一覧」を別途書く**（テンプレ参照）。diff だけを根拠にする体が、一覧との矛盾から範囲の齟齬に気づける余地を作る。
4. judge 側の受け: **「スコープ外の変更がある」型の指摘は、採否の前に必ず範囲を検算する**（`judge_rubric.md`「judge 自身が確かめる」）。

> 同じ「pack に何を入れたか」が原因の型: 2026-08-18 の設計レビューでは `insert_row` の本体を pack に載せていなかったため、pack しか読めない2体が揃って「列が欠落すると DB のデフォルト値が入る」と誤った（実際は全列を明示 INSERT するので NULL）。**パネルの質ではなく司書の手元が原因**という点で上と同じ（→「pack は司書の盲点を継承する」）。

## 2巡目（再レビュー）は「前巡の指摘が閉じたか」を問う形に組む

1巡目で差し戻し、直してから同じ問いを投げ直す型。毎回その場で組むと、judge の突き合わせが「前巡の指摘と今回の回答を人力で対応づける」作業になる。

2026-08-18 の設計レビュー2巡では、2巡目の pack に**1巡目の指摘を ID つきの箇条書きで入れ、閉じたかを問うた**ところ、3体とも**指摘 ID を引いて**「A は閉じていない / C は閉じている」と答え、突き合わせが1巡目より圧倒的に速かった。

1. **前巡の指摘を ID つきで列挙する**（`F1` `F2` …）。要約でなく**指摘の本文**を貼る——ID だけでは pack しか読めない体に中身が届かない。「何を直したか」は本文でなく「材料の版（正本）」欄の SHA 差分で示す。
2. **回答を3分割で要求する**：(a) **前巡の指摘ごとの判定**（ID ごとに 閉じた / 部分 / 閉じていない ＋根拠）(b) **新しい欠陥**（今回の修正が持ち込んだものを含む）(c) **総合判定**。(b) を明示しないと全員が (a) だけを埋め、**修正自身が持ち込んだ欠陥が誰にも見られない**まま通過する。
3. **前巡の judge 成果物を渡す枠と渡さない枠を混ぜない**。渡すなら全枠、渡さないなら全枠。これは新しい規則ではなく **SKILL step 2「全パネリストに完全に同じプロンプトを渡す」の適用**——2巡目は「1巡目の `judge.md` はリポを読める枠だけが読める」形に**黙って**なりやすい（2026-08-18 に実際にそうなった）。
   - **既定は「指摘リストだけを渡し、前巡の judge の判定・重みづけは渡さない」**。judge の結論を配ると全員がそこにアンカーされ、独立実行から収穫するという前提（`panel.md`）が縮む。閉じたかの判定に必要なのは指摘の本文であって、judge がどう重みづけたかではない。
   - どうしても非対称にするなら、**mapping.txt と監査証跡に「どの枠が前巡の judge を見たか」を可視性（3列目）と同じ粒度で書く**。非対称そのものより、非対称が記録されずに合意が読まれることが害。
4. **3分割を要求したら、その見出し語を `check_answer.sh --expect` に渡す**（例: `--expect 閉じ --expect 新しい欠陥`）。2巡目は「1巡目で全部見たから」と作業予告だけ返す体が出やすく、バイト数の検査だけでは通り抜ける（SKILL step 2）。

## 限界
- パネリストは **pack の外を見られない**。pack の質＝回答の上限。重要な証拠の取りこぼしは judge でも回復しない。
- **大きすぎる pack は逆効果**（context rot）。1パネリストの実効コンテキスト窓に収める。入りきらないなら「絞りが甘い」サイン。
- 司書（メイン）が retrieval で握った事実誤りは全パネリストに伝播する。出典つきにして**パネリストが疑える**余地を残す。
- **バックエンドごとに入力サイズの上限が違う**。外部CLIは実装次第で数百KBを通すものもあれば落ちるものもある（run_*.sh 規約「プロンプトを argv に展開しない」を満たしていれば概ね通る）。大型 pack で特定の1体だけが空応答になったら、まず `answer_<label>.err` を見る。
